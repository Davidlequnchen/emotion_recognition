# Linear probe：从原理到运行与论文分析

**一句话：保持大模型不变，拿它处理音频时留下的内部数字，训练一个简单的情绪分类器，看看这些数字能否帮助区分情绪。**

本页先解释为什么做、怎么做、结果说明什么，再介绍服务器上的操作。分析脚本是 [linear_probe.py](linear_probe.py)，设置在 [linear_probe.yaml](../../config/linear_probe.yaml)。

## 1. 我们想回答什么问题？

目前的评测问大模型：“这段音频是什么情绪？”然后检查它生成的 `angry`、`happy` 等答案是否正确。

如果模型经常答错，仅看答案还不能知道问题发生在哪里。它处理音频时产生的内部表示，可能已经包含了有助于区分情绪的规律，但最终生成的词没有很好地反映这些规律；也可能在我们保存的表示中，这些规律本来就不容易读出来。

Linear probe（线性探针）增加了另一种检查方法：让一个很简单的分类器，学习从这些内部表示预测情绪。这个分类器就叫 probe。

可以把它想成：**大模型先写下一页“数字笔记”，我们再训练一个小读者，学习根据笔记判断情绪。** 大模型生成的答案与小读者的答案，是两条不同的输出路径：

```text
音频 + 评测 prompt → 大模型
                       ├─ 原有生成过程 → 一个情绪词 → 原始 LLM 评测
                       └─ 保存的内部向量 → 线性分类器 → probe 评测
```

这里的小读者接受过本数据集的标签训练。因此，probe 是**有监督的诊断实验**，不能把它当成原模型的零样本成绩。这种用独立线性分类器检查内部表示的方法，可参见 [Alain 与 Bengio 的原始论文](https://arxiv.org/abs/1610.01644)。

## 2. 我们保存的 features 到底是什么？

大模型处理输入时，会在各层产生大量数字。对一条音频，我们已经在正式推理时，从若干层中各保存了一条向量，例如：

```text
某条音频、某一层的向量：[0.12, -0.37, 0.84, ...]   # 实际通常有数千个数
```

这些数不是人工提取的“音高、音量、语速”，也没有“第一个数就是愤怒程度”这样的固定含义。它们是模型自己形成的内部表示。

更准确地说，本项目保存的是：**语言模型部分在首次处理输入时，音频 token 所在位置的隐藏状态，再对这些位置取平均。** 一个 token 可以粗略理解为模型处理的一小段输入；平均的作用，是把长短不同的音频统一成固定长度的向量。

需要区分三个概念：

| 概念 | 在本项目中的意思 |
|---|---|
| 一条向量 | 一条音频在某一层的数字表示 |
| 不同层的向量 | 同一条音频在不同处理阶段留下的表示，分别训练 probe |
| `layers: all` | 使用所有**已经保存的层**；当前推理默认保存 4 个分散选取的层，不是整个大模型的每一层 |

这些表示来自语言模型层，**不是音频 encoder 的逐层输出**。即使只平均音频位置，它们仍处在带有 prompt 和候选标签的模型计算中，不能直接称为完全独立于文本的纯声学特征。我们保存的是生成回答前的表示，也不是生成答案之后再提取的表示。

## 3. 为什么叫“线性”？它具体学什么？

“线性”可以先理解为：**对输入的每个数乘一个权重，再加起来，为每种情绪打分。** 分数最高的情绪就是预测。

假设为方便演示，一条向量只有两个数 `[2, 1]`。某个训练好的分类器可能这样打分：

| 情绪 | 示例打分规则 | 代入 `[2, 1]` 后的分数 |
|---|---|---:|
| angry | `2 × 第一个数 − 第二个数` | 3 |
| happy | `−第一个数 + 2 × 第二个数` | 0 |
| neutral | `0.2 × 第一个数 + 0.2 × 第二个数` | 0.6 |
| sad | `−第一个数 − 第二个数` | −3 |

它会选 `angry`。表里的权重只是解释用的例子；真实权重由训练数据学出来，真实向量也远不止两个数。一般形式是：

```text
某类分数 = 权重1 × 数字1 + 权重2 × 数字2 + ... + 偏置
```

训练时，脚本给分类器看很多“向量 + 正确情绪”配对。分类器反复调整权重和偏置，使正确类别获得更高的预测概率。训练结束后，这些参数固定下来，再去预测没参加训练的样本。

我们的具体实现叫 **Logistic Regression（逻辑回归）**。虽然名字里有“回归”，这里做的是情绪分类：先算上面的线性分数，再用 softmax 把多类分数转换成总和为 1 的概率。二分类时使用 sigmoid。没有额外训练的隐藏层；概率转换不改变其线性分类器的性质。

| 部分 | 在 probe 实验里会不会训练？ |
|---|---|
| Gemma / Qwen 的参数 | 不会；大模型保持冻结，本脚本甚至不加载它 |
| 已保存的 feature 向量 | 不会改写，作为固定输入读取 |
| 每个维度的标准化参数 | 由训练集估计，随后固定 |
| 小分类器的权重和偏置 | 会；用训练集情绪标签学习 |

训练目标来自原预测 CSV 的 `acted_emotion`，即原数据集用于评测的情绪真值；不会把 LLM 自己的答案当作正确标签。`listener_vote` 只随结果带出，供后续分析。每个模型、数据集、层分别训练一个分类器，不把三种模型的向量拼起来，也不把所有数据集合并训练。

选简单分类器，是为了检查这些表示能否支持简单的分类规则。不过，“简单”并不代表它没有学习能力，不能把 probe 的表现全部归功于原模型。[Hewitt 与 Liang 的研究](https://aclanthology.org/D19-1275/)讨论了区分表示本身与 probe 学习能力的重要性。

## 4. 我们怎样训练，才能让测试结果有意义？

### 第一步：先分好三份数据，而且按说话人分

| 分区 | 用途 | 会影响什么？ |
|---|---|---|
| train（训练集） | 给分类器看向量与正确标签 | 学习标准化参数、分类器权重和偏置 |
| validation（验证集） | 比较候选设置的效果 | 选择正则化强度和使用哪一层 |
| test（测试集） | 最后检查能否推广到未参与训练、选择的样本 | 用于报告最终表现，不用于调参 |

我们按**说话人**划分。同一个演员的所有句子、情绪强度、麦克风版本，都留在同一份里。否则，分类器可能记住某个人的声音，测试成绩却被误解成对新说话人的情绪识别能力。

例如，有 6 名说话人的数据集，可以让 4 人用于训练、1 人用于验证、1 人用于测试。同一份划分用于所有模型。某个模型缺少 feature 时会报错，不会给它另外挑一份更容易的数据。

默认比例是按说话人数量分为约 60% / 20% / 20%，部分数据集按配置指定人数。由于每人录音数不同，音频条数不一定恰好符合这个比例；脚本会尽量平衡类别，并要求三份都包含每个训练类别。“未见说话人”指本次 probe 训练未见，不保证冻结大模型的预训练从未接触这些公开语料。

### 第二步：只用训练集完成标准化与学习

向量不同维度的数值范围可能差很多。`StandardScaler` 会根据训练集，计算每个维度的平均值和标准差，再将数值减去均值、除以标准差，把各维度调整到较接近的尺度。这样可以避免数值范围特别大的维度过度影响训练。

验证集和测试集只使用训练集算出的规则，不能把它们混进去重新计算。随后，逻辑回归也只用训练集学习。

### 第三步：用验证集选择设置

分类器既要学到规律，也要避免过度记住训练样本。这里用 L2 正则化限制权重，参数名是 `C`：

- `C` 越小，限制越强，分类器更保守。
- `C` 越大，限制越弱，分类器更容易贴合训练数据。

当前每个已保存的层分别尝试 `C = 0.01、0.1、1、10`。先根据验证集表现，为每层选一个 C，再在各层之间选验证集表现最好的一层。同分时保留配置中排在前面的选项。

选择指标是 **UAR**：先分别计算每类有多少样本被识别正确，再对各类的召回率取平均。例如四类召回率是 90%、40%、30%、20%，UAR 就是 45%。这样每个类别分量相同，不会因为 neutral 样本特别多，只识别 neutral 就得到很漂亮的分数。

训练中的 `class_weight: balanced` 则是另一件事：根据**训练集**各类样本数，增加稀少类别的训练权重。它影响学习过程，UAR 影响验证集上的选择与结果评价。

### 第四步：固定选择，再报告测试结果

选好 C 和层以后，不再根据测试成绩改选择，也不会重新用 train + validation 训练。脚本会导出各层的测试成绩，供层间分析；**论文主结果应使用验证集选出的层，不能事后挑测试分数最高的一层。**

`seed` 是控制数据划分随机过程的编号。同一个 seed 和输入可复现同一划分；42 没有特殊科学含义。默认只跑 42，论文可以增加 43、44 等，检查结论对划分是否敏感。少说话人数据集的可行划分有限，不同 seed 也可能选到同一划分，应核对导出的 manifest。

## 5. 怎样理解“原始 LLM vs probe”的结果？

下面是假设情形，不是当前实验结论：

| 观察 | 可以支持的解释 |
|---|---|
| 原始 LLM 较弱，probe 较强 | 保存的表示可以支持一个经过标签训练的线性情绪分类器；值得进一步研究它与原生成答案之间的差异 |
| 两者都较弱 | 当前层、平均方式、线性规则、标签与样本条件下，probe 也未能很好区分情绪 |
| 两者都较强 | 原生成方式和有监督线性分类器，都能在各自设置下完成这批测试 |

第一种情况**不能单独证明**“模型已经听懂，只是分类头坏了”。Probe 额外看过本数据集的训练标签，原始 LLM 在这次零样本评测中没有额外接受这份标签监督；它学会的映射也不代表原生成过程使用了同一套映射。第二种情况也不能证明“音频 encoder 没有情绪信息”或“任何 prompt 都无效”。

比较时需要特别注意：

1. 使用相同的测试音频。`selected_predictions.csv` 含三个分区；先筛选 `split=test`，再按 `audio_path` 与原 LLM 对齐，重新计算原 LLM 在这批音频上的指标。不能直接拿全数据集的原始成绩相减。
2. 报告监督量差异。Probe 结果单独列为有监督诊断，不并入零样本排行榜声称等条件胜出。
3. 核对候选标签。尤其 JL-Corpus：排除复合标签 `excited` 后，probe 学四类；原 LLM 仍是五个候选。即使测试音频相同，候选集合也存在差异，必须写明。
4. 正确理解概率。`probe_p_*` 是新分类器的概率，未额外做概率校准；0.8 不保证现实中恰好有 80% 正确，也不代表大模型自己的置信度。

如果要研究类先验偏好、标签首 token 概率或 prior correction，需要另外的分析。本脚本实现的是线性 probe，不会自动完成这些实验。

## 6. 在公司服务器上怎么运行？

先完成正式 LLM 推理，让预测文件和 features 配套保存在服务器。分析脚本不读音频、不加载 Gemma/Qwen、不使用 GPU；它在 CPU 上读取向量并训练小分类器。系统 RAM 用量取决于数据量和向量维数，逐模型、数据集、层运行也仍需要容纳相应训练矩阵。

在公司服务器的内层 `emotion_recognition/` 目录执行：

```bash
conda activate emotion_recognition_llm
pip install -r requirements.txt

# 先检查输入、特征和数据划分；不训练，不写结果目录。
python scripts/analysis/linear_probe.py --dry-run

# 检查通过后，按 config/linear_probe.yaml 训练并导出。
python scripts/analysis/linear_probe.py
```

也可以先选择一个模型、一个数据集，或重复几个划分：

```bash
python scripts/analysis/linear_probe.py --models gemma4_e4b --datasets crema_d --seeds 42 43 44
```

`--dry-run` 也会扫描向量，检查损坏和非有限值，因此大文件上可能需要一些时间。若检查失败，先按报错处理缺失文件或协议问题，不要为了通过检查随意关闭保护设置。

需要保留的输入：

```text
outputs/<model>/<dataset>_predictions.csv
outputs/<model>/<dataset>_predictions.json
features/<model>/<dataset>/<prompt_hash>/hidden.f16
features/<model>/<dataset>/<prompt_hash>/index.jsonl
features/<model>/<dataset>/<prompt_hash>/meta.json
```

还需要相同版本的 `config/models.yaml`、`config/llm.yaml`、prompt 文件，以及识别说话人所需的元数据：THAI-SER 的 `labels.csv`、Emozionalmente 的 `samples.csv`。其他数据集按已核对的文件名识别说话人。

## 7. 跑完先看哪些文件？带回什么？

每次运行会在 `outputs/linear_probe/` 下新建一个以 UTC 时间命名的目录，不覆盖已有结果。

**先看 `summary.csv` 中 `selected=true` 的行，再看对应 `selected_predictions.csv` 中 `split=test` 的音频。** 前者用于整理主结果表，后者用于对齐原 LLM、查错例和绘图。

| 文件（相对本次运行目录） | 用途 |
|---|---|
| `summary.csv` / `summary.json` | 各模型、数据集、seed、层的指标及选中标记；JSON 另记录跳过和失败原因 |
| `splits/<dataset>/seed_42.csv` | 每条音频的真值、说话人/对话组、所属分区；保存实际使用的划分 |
| `splits/<dataset>/seed_42.json` | 划分来源、类别、各分区数量及用于核对一致性的 hash |
| `splits/<dataset>/excluded_targets.csv` | 因复合真值等原因未进入训练和测试的音频 |
| `<model>/<dataset>/seed_42/selected.json` | 验证集选了哪一层、哪个 C，以及结果适用范围 |
| `<model>/<dataset>/seed_42/selected_predictions.csv` | 选中层的逐音频真值、预测、概率、分区、组别及原 LLM 答案 |
| `<model>/<dataset>/seed_42/layer_<N>/` | 该层三个分区的逐条结果、指标、参数搜索记录及线性参数 |
| `run_config.json` / `source_configuration.json` | 实际运行设置、环境、代码 commit，以及配置和 prompt 原文 |
| `<model>/<dataset>/coverage.json` | 预测文件与 features 的样本是否完整对应 |

每层的 `metrics.json` 保存 Accuracy、UAR、macro-F1、log loss、Brier score 和混淆矩阵。主文可以先用 UAR、macro-F1、Accuracy；概率指标和混淆矩阵供后续分析。`config.json` 保存输入来源、hash、C 搜索和收敛记录；`model_parameters.json` 保存权重、偏置和标准化参数。

**把本次生成的整个 CSV/JSON 目录带回 Mac，同时带回原 LLM 评测的 CSV、JSON、`responses.jsonl`。** 它们足以在本机整理表格、按音频对齐、做错误分析，并支持后续实现配对统计与分组 bootstrap。当前 probe 脚本导出分析所需材料，不自动完成所有统计检验和论文绘图。

`hidden.f16` 留在公司服务器。导出不复制、转成文本或编码原始向量；导出的分类器参数也不是逐音频 feature。以后若需要改用新的分类器或池化方式，仍应在能访问相应 features 的服务器上处理；新的池化方式可能需要重新提取特征。

还要区分原始 LLM 的几种列：

- `probe_p_<label>`：本次小分类器的预测概率。
- 原 LLM CSV 的 `p_<label>`：生成答案的 one-hot 记录，例如答 angry 就是 angry=1，其余=0，不能当成置信度。
- 原 LLM 的 `token_p_*`、`token_mass`：标签首 token 的概率代理，含义与 probe 概率不同，仍保存在原评测输出中。

## 8. 为什么有些数据集会被跳过或排除部分样本？

| 情形 | 当前处理 | 原因 |
|---|---|---|
| TESS | 默认跳过 | 只有两名说话人，无法分成训练、验证、测试三份且身份互不重叠 |
| MELD | 默认跳过 | 目前本项目只有官方 test 的 features，不能在其上训练后仍称官方测试集成绩 |
| JL-Corpus 的 `excited` | 排除这部分音频，并记录原因及可接受标签 | 原评测将其视为可对应 happy 或 surprised 的复合真值；不擅自改成单一训练标签 |
| 某个模型缺 feature | 报错，记录覆盖情况 | 不因缺文件而改变该模型的测试样本 |
| 特征实际平均了整个 prompt | 默认拒绝 | 避免与按音频位置平均的表示混为同一种实验 |

若只是想对 MELD 现有 test 数据做**额外探索**，可以提供按 dialogue 分组的显式划分，并设 `allow_test_only_diagnostics: true`。输出会标为 `diagnostic_only_official_test_dialogues`。不同对话仍可能出现同一个角色，因此不等于说话人互斥，也不能作为官方 held-out 泛化成绩。正式 MELD probe 需要另行准备 train/dev 等特征并制定对应划分，当前 test-only 流程不提供这种正式评测。

## 9. 配置速查与复现

通常先用默认配置，只通过命令行选择模型、数据集与 seeds。完整设置在 [linear_probe.yaml](../../config/linear_probe.yaml)：

| 设置 | 白话解释 |
|---|---|
| `models` / `datasets` | 分析哪些已完成正式评测的模型和数据集 |
| `seeds` | 重复哪些随机划分；不是大模型生成时的温度或随机种子 |
| `layers` | 比较哪些已保存的语言模型层；`all` 不会重新提取其他层 |
| `c_values` | 让验证集选择的正则化候选值 |
| `max_iter` / `require_convergence` | 学习最多迭代多少次；若某层选中分类器未收敛，默认报错，避免报告尚未训练到位的结果 |
| `group_counts` | 特定数据集的训练/验证/测试人数，优先于默认比例 |
| `split_manifests` | 指定已经核对的划分 CSV；为空则自动生成并导出 |
| `require_current_protocol` | 核对模型、prompt、候选标签与当前评测设置是否匹配 |
| `require_audio_pooling` | 要求使用音频位置的平均表示 |
| `hash_features` | 读取特征文件计算 SHA-256，记录这次到底用了哪一份输入；不导出向量 |
| `num_threads` / `prediction_batch_size` | CPU 线程数和分批预测条数，主要影响资源使用 |

显式划分 CSV 至少需要 `audio_path,group,split`，可附 `seed`。`group` 必须与脚本识别出的身份一致，`split` 为 `train`、`validation`、`test`。每条符合条件的音频恰好出现一次，每类在三份中都有样本。可以把第一次导出的划分填入 `split_manifests`，以后固定复用。

脚本还会核对完整正式评测的协议、文件路径、索引、二进制长度、层号、模型和 prompt hash，拒绝旧协议、`_sampleN` 试跑、损坏向量与不完整覆盖。发生部分失败时，会保留已完成的导出及失败清单；修复原因后使用新目录重跑。

默认一次 seed 只能给出一次说话人划分下的结果。重复 seeds 可以检查结论是否依赖划分；估计不确定性时，还要考虑同一说话人的多条录音并非独立样本。

```bash
python -m unittest discover -s test_scripts -p 'test_linear_probe.py' -v
```
